## 1. Overview

All users are required to set up TOTP-based two-factor authentication (compatible with Google Authenticator, Authy, etc.) as part of their account activation. 2FA is not optional — users cannot skip or disable it themselves. This is enforced via a mandatory setup step on first login and a TOTP verification step on every subsequent login.

The system uses Better-Auth's built-in `twoFactor` plugin, which handles TOTP secret generation, QR code URIs, backup codes, and verification.

### Key Concepts

- **TOTP (Time-based One-Time Password)**: A 6-digit code that changes every 30 seconds, generated by the user's authenticator app from a shared secret.
- **Backup Codes**: 10 single-use recovery codes generated at setup time. Used when the user loses access to their authenticator app.
- **Trusted Device**: When a user verifies their TOTP code, they can optionally mark the device as trusted for 30 days to skip the 2FA step on that browser.
- **2FA Reset**: An admin action that clears a user's 2FA configuration, forcing them to re-setup on next login.

## 2. Business Rules

1. **2FA is mandatory for all roles.** Every user (super_admin, admin, branch_manager) must complete 2FA setup before accessing the application.
2. **Users cannot disable their own 2FA.** There is no self-service disable option. Once set up, 2FA remains active.
3. **First login forces 2FA setup.** After account creation, the user's first successful password login redirects them to a mandatory 2FA setup page. They cannot navigate away or access any application page until setup is complete.
4. **Setup requires TOTP verification.** The user must scan the QR code and enter a valid 6-digit code from their authenticator app to complete setup. This proves the authenticator is configured correctly.
5. **Backup codes are shown once at setup time.** 10 codes, each 10 characters. The user must save them — they are never displayed again (stored encrypted server-side). Each backup code is single-use.
6. **Backup codes can be regenerated.** From the user's security settings, requiring their current password. Old codes are invalidated, new codes are shown once.
7. **Trusted device is optional.** During TOTP verification at login, the user can check "Trust this device" to skip 2FA for 30 days on that browser.
8. **Admin can reset a user's 2FA.** For account recovery when a user loses their phone. This removes their TOTP secret and backup codes, setting them back to the "needs setup" state. The user must re-setup 2FA on their next login.
9. **Super admin can reset any user's 2FA.** Across all organizations.
10. **Admin can only reset 2FA for users in their own organization.** Standard tenant isolation rules apply.
11. **2FA verification cookie expires in 10 minutes.** If the user doesn't complete the TOTP step within 10 minutes of entering their password, they must sign in again.
12. **Rate limiting on TOTP verification.** Better-Auth enforces built-in rate limiting to prevent brute-force on the 6-digit code window.
13. **Enabling 2FA requires the user's current password.** The enable endpoint validates the password before generating the TOTP secret.

## 3. Data Model Changes

### 3.1 Modified: `user` table

| Column | Type | Default | Description |
|---|---|---|---|
| `twoFactorEnabled` | `Boolean` | `false` | Whether the user has completed 2FA setup. `false` on new accounts — flips to `true` after first TOTP verification during setup. |

### 3.2 New: `two_factor` table

| Column | Type | Description |
|---|---|---|
| `id` | `String` (PK) | Auto-generated (cuid) |
| `userId` | `String` (FK -> user, unique) | The user this record belongs to. One record per user. |
| `secret` | `String` | Encrypted TOTP secret. Never returned to the client. |
| `backupCodes` | `String` | Encrypted backup codes (JSON array). Never returned directly — only decrypted server-side when verifying or regenerating. |
| `verified` | `Boolean` | Default `true`. Internal flag used by Better-Auth. |

> **Note:** This table has no `organizationId` column. Tenant isolation is inherited through `userId` — the user is already organization-scoped. Better-Auth manages this table internally; we only provide the Prisma model and migration.

### 3.3 Prisma Model

```prisma
// Added to api/prisma/models/auth.prisma

model TwoFactor {
  id          String  @id @default(cuid())
  secret      String
  backupCodes String
  userId      String
  user        User    @relation(fields: [userId], references: [id], onDelete: Cascade)
  verified    Boolean @default(true)

  @@index([userId])
  @@map("two_factor")
}
```

The `User` model gains:

```prisma
twoFactorEnabled Boolean    @default(false)
twoFactor        TwoFactor?
```

### 3.4 Modified: `AuditAction` enum

```prisma
enum AuditAction {
  // ... existing values ...
  USER_2FA_RESET
}
```

## 4. API Endpoints

### 4.1 Better-Auth Plugin Endpoints (automatic)

All served under `/api/auth/` and handled by the `twoFactor` plugin:

| Endpoint | Method | Auth | Body | Response | Description |
|---|---|---|---|---|---|
| `/api/auth/two-factor/enable` | POST | Session | `{ password }` | `{ totpURI, backupCodes[] }` | Generates TOTP secret, returns URI for QR code and backup codes |
| `/api/auth/two-factor/verify-totp` | POST | 2FA cookie | `{ code, trustDevice? }` | `{ token, user }` | Verifies 6-digit TOTP code during login |
| `/api/auth/two-factor/verify-backup-code` | POST | 2FA cookie | `{ code }` | `{ token, user }` | Verifies a backup code during login (single-use) |
| `/api/auth/two-factor/generate-backup-codes` | POST | Session | `{ password }` | `{ backupCodes[] }` | Regenerates backup codes (invalidates old ones) |
| `/api/auth/two-factor/get-totp-uri` | POST | Session | `{ password }` | `{ totpURI }` | Re-fetches the TOTP URI (for re-scanning QR) |

> **Note:** The `/disable` endpoint exists in the plugin but will not be exposed on the client. The frontend never calls it. Only the admin reset endpoint (below) can remove a user's 2FA.

### 4.2 Custom Endpoint (NestJS)

| Endpoint | Method | Auth | Description |
|---|---|---|---|
| `PATCH /api/users/:id/two-factor` | PATCH | Admin/Super Admin session | Resets (disables) another user's 2FA. Deletes their `two_factor` record and sets `twoFactorEnabled = false`. Creates an audit log entry. |

**Authorization rules:**
- `super_admin`: can reset any user's 2FA
- `admin`: can only reset 2FA for users in their own organization
- `branch_manager`: no access (403)
- Cannot reset your own 2FA through this endpoint

## 5. Authentication Flows

### 5.1 New User — First Login (2FA Setup Required)

```
1. Admin creates new user account
   └─ user.twoFactorEnabled = false (no two_factor record exists)

2. New user signs in with email + password
   └─ Password valid → session granted
   └─ Client checks: user.twoFactorEnabled === false

3. Client redirects to /setup-2fa (mandatory setup page)
   └─ User cannot navigate to any other app page
   └─ App shell / layout enforces the redirect

4. Setup page:
   a. User enters current password
   b. POST /api/auth/two-factor/enable { password }
   c. Server returns { totpURI, backupCodes[] }
   d. Page renders QR code from totpURI
   e. User scans QR with Google Authenticator
   f. User enters 6-digit verification code
   g. Page saves backup codes display

5. Setup complete → user.twoFactorEnabled = true
   └─ Redirect to dashboard
```

### 5.2 Returning User — Login with 2FA

```
1. User enters email + password on login page

2. Better-Auth validates credentials
   └─ user.twoFactorEnabled === true
   └─ Returns { twoFactorRedirect: true } (no session yet)
   └─ Sets a temporary 2FA verification cookie (10 min TTL)

3. Client redirects to /login/verify-2fa

4. User enters 6-digit code from authenticator app
   └─ POST /api/auth/two-factor/verify-totp { code, trustDevice? }

5a. Code valid → full session granted → redirect to dashboard
5b. Code invalid → error message, user retries

6. Alternative: user clicks "Use a backup code"
   └─ POST /api/auth/two-factor/verify-backup-code { code }
   └─ Code valid + consumed → session granted
```

### 5.3 Returning User — Trusted Device

```
1. User previously checked "Trust this device" (within 30 days)

2. User enters email + password

3. Better-Auth detects trusted device cookie
   └─ Skips 2FA step entirely
   └─ Session granted → redirect to dashboard
```

### 5.4 Admin Resets User's 2FA

```
1. User loses phone / authenticator app
   └─ Cannot log in (no TOTP code, no backup codes)

2. User contacts admin

3. Admin navigates to Users → selects user
   └─ Sees "2FA Active" badge on the user

4. Admin clicks "Reset 2FA"
   └─ Confirmation dialog: "This will remove 2FA for [user name].
      They will be required to set up a new authenticator on their
      next login."

5. PATCH /api/users/:id/two-factor
   └─ Deletes two_factor record
   └─ Sets user.twoFactorEnabled = false
   └─ Creates audit log: USER_2FA_RESET

6. User can now log in with just email + password
   └─ After login, forced to /setup-2fa (flow 5.1 resumes at step 3)
```

### 5.5 Regenerate Backup Codes

```
1. User goes to Settings → Profile → Security section

2. Clicks "Regenerate backup codes"

3. Enters current password

4. POST /api/auth/two-factor/generate-backup-codes { password }
   └─ Old codes are invalidated
   └─ Returns new { backupCodes[] }

5. New codes displayed once with copy/download option
```

## 6. User Stories

### All Users

| ID | Story |
|---|---|
| 2FA-01 | As a new user, I am required to set up two-factor authentication on my first login so that my account is secured from the start. |
| 2FA-02 | As a returning user, I want to enter my authenticator code after my password so that my account is protected even if my password is compromised. |
| 2FA-03 | As a user who lost my phone, I want to use a backup code to sign in so that I am not permanently locked out. |
| 2FA-04 | As a user, I want to mark my device as trusted so that I don't have to enter a code every time on my personal computer. |
| 2FA-05 | As a user, I want to regenerate my backup codes so that I can replace codes I've used or lost. |
| 2FA-06 | As a user, I want to view my QR code again from settings so that I can add my account to a new phone's authenticator app. |

### Admin

| ID | Story |
|---|---|
| 2FA-07 | As an admin, I want to reset a user's 2FA so that they can regain access after losing their authenticator device. |
| 2FA-08 | As an admin, I want to see which users have 2FA set up so that I can identify users who haven't completed setup. |

### Super Admin

| ID | Story |
|---|---|
| 2FA-09 | As a super admin, I want to reset any user's 2FA across any organization for platform-level support. |

## 7. Page Specifications

### 7.1 2FA Setup Page (`/setup-2fa`)

**Access:** Authenticated users with `twoFactorEnabled === false` only. Users with 2FA already active are redirected to dashboard.

**Layout:** Centered card (similar to login page), no sidebar/app shell. The user cannot navigate away.

**Steps (wizard-style):**

**Step 1 — Enter Password**
- Heading: "Set up two-factor authentication"
- Subtext: "Two-factor authentication adds an extra layer of security to your account."
- Password input field
- "Continue" button
- On submit: calls `/api/auth/two-factor/enable` with password

**Step 2 — Scan QR Code**
- Heading: "Scan this QR code"
- Subtext: "Use Google Authenticator or any TOTP app to scan this code."
- QR code rendered from `totpURI`
- Fallback: "Can't scan? Click to show the secret key" (shows the TOTP secret as copyable text)
- 6-digit code input field (auto-focus, large centered digits)
- "Verify & activate" button
- On submit: verifies the entered code matches the TOTP (client-side verification against the active session — the enable endpoint already activated 2FA, this step confirms the user's app is working)

**Step 3 — Save Backup Codes**
- Heading: "Save your backup codes"
- Subtext: "Each code can only be used once. Store them in a safe place."
- Grid of 10 codes displayed in a monospace font
- "Copy all" button (copies to clipboard)
- "Download as .txt" button (downloads a text file)
- Checkbox: "I have saved my backup codes"
- "Continue to app" button (disabled until checkbox is checked)
- On click: redirects to dashboard

### 7.2 TOTP Verification Page (`/login/verify-2fa`)

**Access:** Users in the 2FA verification step (have a valid 2FA cookie from password auth).

**Layout:** Centered card (same style as login page). No sidebar/app shell.

**Content:**
- Heading: "Two-factor authentication"
- Subtext: "Enter the 6-digit code from your authenticator app"
- 6-digit code input (auto-focus, large centered digits)
- Checkbox: "Trust this device for 30 days"
- "Verify" button
- Link: "Use a backup code instead" (toggles to a backup code input)
- Error display for invalid codes
- "Back to sign in" link (returns to login, clears 2FA cookie)

**Backup code mode:**
- Heading: "Enter a backup code"
- Subtext: "Enter one of your 10-character backup codes"
- Single text input for the backup code
- "Verify" button
- Link: "Use authenticator code instead" (toggles back)

### 7.3 Profile Settings — Security Section

**Location:** `/settings/profile` — existing Security card, expanded.

**Current state (2FA active):**
- Status line: "Two-factor authentication" with a green "Active" badge
- Button: "View QR code" — opens modal, requires password, shows QR code for re-scanning
- Button: "Regenerate backup codes" — opens modal, requires password, shows new codes
- Info text: "Two-factor authentication is required for all accounts and cannot be disabled."

### 7.4 Users Table — 2FA Column

**Location:** `/users` — admin users list.

**Changes:**
- New column or badge: "2FA" showing status
  - Green badge "Active" if `twoFactorEnabled === true`
  - Yellow badge "Pending" if `twoFactorEnabled === false`
- Row action (for admins viewing other users): "Reset 2FA" button
  - Only visible when user has `twoFactorEnabled === true`
  - Opens confirmation dialog

**Reset 2FA Confirmation Dialog:**
- Title: "Reset two-factor authentication"
- Body: "This will remove two-factor authentication for **[user name]**. They will be required to set up a new authenticator app on their next login."
- Buttons: "Cancel" / "Reset 2FA" (destructive style)

## 8. Audit Trail

### 8.1 New Audit Action

| Event | Trigger | Actor | entity_type | old_value | new_value |
|---|---|---|---|---|---|
| `USER_2FA_RESET` | Admin resets another user's 2FA | Admin who performed the reset | `user` | `{ twoFactorEnabled: true }` | `{ twoFactorEnabled: false, resetBy: "<admin_id>" }` |

### 8.2 Existing Audit Coverage

The user's own 2FA setup (via Better-Auth's enable endpoint) does not create a custom audit entry. It is a self-service action within an authenticated session and is tracked by Better-Auth's internal mechanisms.
